# Kepler's First Law — 2D Orbital Simulation

## Overview

This GNU Octave prototype models the two-dimensional motion of a planet orbiting a fixed central star under Newtonian gravity. Its purpose is to demonstrate Kepler's First Law: for a bound orbit in an ideal inverse-square gravitational field, the orbit is an ellipse with the central star at one focus.

The program accepts the star's mass, the planet's mass, the planet's initial position and velocity, the integration time step, and the requested simulation duration. It validates these inputs, calculates the analytical properties of the corresponding bound ellipse, integrates the planet's trajectory using two numerical methods, and reports physical quantities and numerical diagnostics.

**Velocity Verlet** is the primary integration method. **Semi-implicit Euler** is retained as a comparison method. Both use the same fixed-star gravitational acceleration model and initial conditions.

The analytical ellipse is calculated from the initial conditions independently of either numerical trajectory. The program plots this ellipse alongside the numerical trajectories and compares numerical distances, speeds, energy, angular momentum, and the positions produced by the two integration methods.

This prototype is intended as a scientific and educational foundation for AstPIE. It is a simplified orbital model, not a general-purpose N-body simulator.

## Physical Model

### Coordinate system and bodies

Motion is represented in a two-dimensional Cartesian coordinate system. The central star remains fixed at the origin:

- Star position: `r_star = [0, 0]`.
- Planet position: `r = [x, y]` metres.
- Planet velocity: `v = [vx, vy]` metres per second.
- Planet acceleration: `a = [ax, ay]` metres per second squared.

The star is treated as the focus of the intended orbit. The simulation neglects the star's motion around the system barycentre, so it uses the fixed-star approximation rather than solving the exact two-body problem.

### Gravitational parameter

The program defines the gravitational constant as:

`G = 6.67430e-11 m^3 kg^-1 s^-2`

The gravitational parameter is calculated from the star's mass:

`mu = G * M_star`

Here, `M_star` is the central star's mass in kilograms and `mu` is measured in cubic metres per second squared.

The planet's mass is accepted and displayed, but it is **not used in the equations of motion**. Under the fixed-star approximation, the planet is treated as a test body moving in the star's gravitational field. The model does not calculate the mutual motion of the star and planet.

### Gravitational acceleration

Let `r = [x, y]` be the planet's position relative to the star and let `r_mag` be its distance from the origin. The acceleration is directed towards the star and follows the inverse-square gravitational law:

`r_mag = sqrt(x^2 + y^2)`

`a = -(mu / r_mag^3) * r`

In component form:

`ax = -mu * x / r_mag^3`

`ay = -mu * y / r_mag^3`

The model includes no other planets, atmospheric drag, thrust, relativistic corrections, non-spherical gravity, or other forces. The central star is treated as a point mass.

## Analytical Orbital Properties

The program derives the theoretical orbital properties from the initial position and velocity. These calculations do not depend on the trajectory generated by Euler or Velocity Verlet.

### Initial distance and speed squared

For an initial position `r0 = [x0, y0]` and initial velocity `v0 = [vx0, vy0]`:

`r0_mag = sqrt(x0^2 + y0^2)`

`v0_squared = vx0^2 + vy0^2`

The initial position must not be at the star, because the point-mass gravitational acceleration is singular at zero separation.

### Specific orbital energy

The initial specific orbital energy is calculated as:

`epsilon = v0_squared / 2 - mu / r0_mag`

Specific orbital energy is energy per unit mass, measured in square metres per square second (`m^2/s^2`). In the two-body Kepler model, negative specific energy corresponds to a bound orbit. The program therefore rejects initial conditions with `epsilon >= 0` and proceeds only with bound-orbit cases.

### Specific angular momentum

In two dimensions, the scalar z-component of specific angular momentum is:

`h = x0 * vy0 - y0 * vx0`

Its units are square metres per second (`m^2/s`). The program rejects `h = 0`, which corresponds to a radial trajectory in this model. It does not attempt to construct an elliptical orbit from radial initial conditions.

### Eccentricity

The orbital eccentricity is calculated from specific energy and specific angular momentum:

`e_squared = 1 + (2 * epsilon * h^2) / mu^2`

`e = sqrt(e_squared)`

The program checks that the resulting value is finite and satisfies `0 <= e < 1`, as required for an ellipse. A circular orbit is the limiting case `e = 0`; larger eccentricities describe increasingly elongated ellipses.

The program also calculates the eccentricity vector. This vector points in the direction of perihelion for a non-circular orbit and is used to orient the analytical ellipse:

`r_dot_v = x0 * vx0 + y0 * vy0`

`e_vec = (((v0_squared - mu / r0_mag) * r0) - (r_dot_v * v0)) / mu`

The components of this vector are calculated separately in the program. Its direction is obtained using `atan2(e_y, e_x)`. For a nearly circular orbit, the program sets the orientation angle to zero because the perihelion direction is numerically ill-defined when eccentricity is effectively zero.

### Ellipse dimensions and distances

The semi-major axis is calculated from specific orbital energy:

`a = -mu / (2 * epsilon)`

The semi-minor axis is:

`b = a * sqrt(1 - e^2)`

The focal distance (distance from the ellipse centre to either focus) is:

`c = a * e`

The analytical perihelion distance, the closest orbital distance to the star, is:

`r_peri = a * (1 - e)`

The analytical aphelion distance, the farthest orbital distance from the star, is:

`r_apo = a * (1 + e)`

The terms *perihelion* and *aphelion* are appropriate for an orbit around a star. More generally, these distances are called periapsis and apoapsis.

## Analytical Ellipse Construction

The program constructs a geometric reference ellipse using 3,601 sample values of an ellipse parameter `E` from `0` to `2*pi`. This parameter is used to trace the ellipse; it is not calculated as a time-dependent orbital solution.

Before rotation, the ellipse is centred at `(-c, 0)` relative to the star-at-origin coordinate system:

`x_local = a * cos(E) - c`

`y_local = b * sin(E)`

The coordinates are then rotated through the perihelion direction angle `omega`:

`x_ellipse = x_local * cos(omega) - y_local * sin(omega)`

`y_ellipse = x_local * sin(omega) + y_local * cos(omega)`

This construction places the star at one focus of the ellipse. For an exactly circular orbit, `c = 0`, so the ellipse becomes a circle and the focus coincides with its centre.

The sampled ellipse is a **geometric reference**, not a list of analytical planet positions at the same timestamps as the numerical integration. The code does not solve Kepler's equation to calculate a time-matched analytical position history.

## Numerical Simulation and Time History

### Inputs and validation

The program prompts for:

| Input        | Meaning                 			    | Unit / format                                |
|--------------|----------------------------------------------------|----------------------------------------------|
| `star_mass`  | Central star mass 				    | 			Positive finite scalar, kg |
| `planet_mass`| Planet mass, reported but not used in acceleration | Positive finite scalar, kg                   |
| `r0_planet`  | Initial planet position                            | Two-component real finite vector, m          |
| `v0_planet`  | Initial planet velocity                            | Two-component real finite vector, m/s        |
| `dt`         | Integration time step                              | Positive finite scalar, s                    |
| `T`          | Requested simulation duration                      | Positive finite scalar, s                    |

Position and velocity inputs are converted to row vectors after validation. The program rejects non-real or non-finite vector components, vectors with the wrong number of components, non-positive masses, a zero initial distance, non-positive time steps, and non-positive durations.

The requested duration must be an integer multiple of the time step within the program's numerical tolerance. The number of integration steps is rounded from `T / dt`, and the actual simulated duration is calculated as `num_steps * dt`.

The time-history array is constructed as:

`time_history = (0:num_steps)' * dt`

There are `num_steps + 1` stored states because the initial state at time zero is included before the integration loop starts.

### Stored arrays

For each numerical method, the program stores the planet's position, velocity, and acceleration at every simulation timestamp. It then calculates the distance from the star and the speed from the stored vectors.

The Velocity Verlet histories use the following array names:

- `planet_positions`
- `planet_velocities`
- `planet_accelerations`
- `verlet_distance_history`
- `verlet_speed_history`

The semi-implicit Euler histories use:

- `euler_planet_positions`
- `euler_planet_velocities`
- `euler_planet_accelerations`
- `distance_history`
- `speed_history`

Each position, velocity, and acceleration row corresponds to a timestamp in `time_history`.

## Semi-Implicit Euler Integration

Semi-implicit Euler is retained as a comparison method. At the beginning of a time step, the acceleration is calculated from the current position. Velocity is then updated before position:

`v_next = v + a * dt`

`r_next = r + v_next * dt`

The acceleration for the next stored state is calculated from the updated position using the same gravitational model:

`a_next = -(mu / |r_next|^3) * r_next`

This update order distinguishes semi-implicit Euler from explicit Euler, which advances position using the old velocity. Semi-implicit Euler is simple, but it generally introduces noticeable orbital energy and trajectory errors that accumulate with integration time and depend on the selected time step.

The method is not treated as the primary result; it provides a reference for comparing the behaviour of a different numerical integration scheme.

---

## Velocity Verlet Integration

Velocity Verlet is the primary integration method. During each time step, the program first calculates the new position using the current position, velocity, and acceleration:

`r_next = r + v * dt + 0.5 * a * dt^2`

It then calculates the gravitational acceleration at that new position:

`a_next = -(mu / |r_next|^3) * r_next`

Finally, it updates the velocity using the average of the current and next accelerations:

`v_next = v + 0.5 * (a + a_next) * dt`

The new position, velocity, and acceleration are saved in the corresponding histories. The acceleration depends on position, so it is recalculated after each position update.

Velocity Verlet is a time-reversible, second-order method for suitable position-dependent forces and often has good long-term behaviour in conservative orbital systems. It is not exact and is not guaranteed to outperform every other method in every problem. Its accuracy depends on the time step, initial conditions, duration, and numerical implementation.

## Numerical Diagnostics

### Distance and speed

At each stored time, the distance and speed are calculated from vector components:

`r_mag = sqrt(x^2 + y^2)`

`speed = sqrt(vx^2 + vy^2)`

The distance is measured in metres and speed in metres per second.

### Specific energy and angular momentum histories

The code recalculates specific orbital energy from each numerical state:

`epsilon_i = speed_i^2 / 2 - mu / r_mag_i`

It calculates the specific angular momentum history as:

`h_i = x_i * vy_i - y_i * vx_i`

These quantities should be constant for the ideal continuous Kepler problem. Their variations along a numerical trajectory therefore provide useful diagnostics of integration behaviour.

For each method, the program first calculates the difference from its own initial value:

`energy_error_i = epsilon_i - epsilon_0`

`angular_momentum_error_i = h_i - h_0`

It then calculates the maximum absolute error and expresses it relative to the magnitude of the initial quantity:

`maximum_relative_energy_error_percent = 100 * max(abs(energy_error)) / abs(epsilon_0)`

`maximum_relative_angular_momentum_error_percent = 100 * max(abs(angular_momentum_error)) / abs(h_0)`

The output and plots show the magnitude of these relative errors. A small error indicates stronger numerical conservation for the run, but does not by itself prove that every aspect of the trajectory is accurate.

### Observed distance extrema

The program finds the minimum and maximum values in the Velocity Verlet distance history. It records their indices, times, positions, and velocities.

`minimum_distance = min(verlet_distance_history)`

`maximum_distance = max(verlet_distance_history)`

The observed numerical minimum is compared with analytical perihelion distance, and the observed numerical maximum is compared with analytical aphelion distance. The signed differences are:

`perihelion_distance_error = minimum_distance - r_peri`

`aphelion_distance_error = maximum_distance - r_apo`

The program also reports the absolute percentage differences using the corresponding analytical distances as denominators.

These observed extrema apply only to the simulated time interval. If the simulation duration does not include perihelion or aphelion, the numerical minimum or maximum may not capture the true orbital extremum. The output should therefore be interpreted alongside the selected duration and the initial conditions.

### Distance to the sampled analytical ellipse

For each numerical position, the program calculates its distance to every sampled point on the analytical ellipse and stores the smallest of those distances. In mathematical terms, for numerical point `r_i` and sampled ellipse points `q_j`:

`d_ellipse_i = min_j sqrt((q_x_j - x_i)^2 + (q_y_j - y_i)^2)`

The program reports the maximum and mean of these values for Euler and Velocity Verlet.

This is a **geometric distance to a sampled curve**, not a time-matched analytical position error. Its result also depends on the density of the ellipse samples (3,601 points in the current implementation). The curve is sampled densely, but the nearest sampled point is not necessarily the exact closest point on the continuous ellipse.

### Direct comparison between integration methods

The code calculates the Euclidean distance between the Euler and Velocity Verlet positions at each matching timestamp:

`position_difference_i = sqrt((x_euler_i - x_verlet_i)^2 + (y_euler_i - y_verlet_i)^2)`

It reports the maximum and mean position difference and the timestamp at which the maximum difference occurs. This comparison measures disagreement between the two numerical methods; it is not an independent proof that either method is exact.

## Graphs and Visualisation

The script generates several figures using the stored simulation data.

### Velocity Verlet trajectory and analytical ellipse

The first trajectory plot shows the Velocity Verlet path, the analytical ellipse, the star at the origin, the initial and final positions, and the observed minimum- and maximum-distance positions. `axis equal` keeps the x and y scales equal so the shape is not geometrically distorted.

### Numerical trajectories — zoomed view

The zoomed trajectory plot compares the semi-implicit Euler and Velocity Verlet paths over the selected simulation duration. Its plotting limits are based on the numerical positions, which helps show the difference between the paths even when the full theoretical ellipse spans a much larger area.

### Position components versus time

Two subplots show the Velocity Verlet x-position and y-position as functions of time.

### Distance and speed comparisons

Separate figures compare the distance from the star and the speed for Euler and Velocity Verlet over the full run.

### Energy and angular-momentum conservation

Separate plots display the absolute relative energy error and absolute relative angular-momentum error, in percent, for both numerical methods.

### Distance to the analytical ellipse

The plot compares the geometric distance to the sampled ellipse for each method. Because these are nearest-point distances to the sampled geometric curve, this plot should not be interpreted as a time-matched trajectory-error plot. For clarity, a suitable title is **“Distance to Sampled Analytical Ellipse”** and a suitable vertical-axis label is **“Geometric Distance (m)”**.

### Position difference between methods

This plot shows the separation between the two numerical positions at each shared timestamp and marks the maximum difference.

### Analytical parameter summary

A final text figure displays eccentricity, semi-major and semi-minor axes, focal distance, analytical perihelion and aphelion distances, and the Velocity Verlet mean and maximum geometric distance to the sampled ellipse.

## Validation and Testing

The script includes runtime validation for the input parameters and checks for invalid distances and non-finite numerical states during integration. It also calculates diagnostics that help evaluate energy conservation, angular-momentum conservation, orbit dimensions, observed radial extrema, and agreement between the two numerical methods.

A repeatable validation process should include the following cases:

- A circular orbit (`e` approximately zero).
- A moderately eccentric bound ellipse.
- A highly eccentric but still bound ellipse, using a time step small enough to resolve perihelion passage.
- Invalid or non-finite masses, time steps, durations, and vector components.
- Position and velocity inputs with the wrong dimensions.
- An initial position at the star.
- Zero initial velocity, which should be rejected if it produces a radial trajectory or non-elliptical energy condition.
- An unbound initial condition with non-negative specific orbital energy.
- A radial initial condition with zero specific angular momentum.
- A duration shorter than one time step or not an integer multiple of the time step.
- A run that does not cover a complete orbit, to ensure observed extrema are not mistaken for theoretical extrema.
- Repeated runs with smaller time steps while keeping the physical initial conditions and total duration fixed.
- Comparison of the analytical ellipse geometry and the calculated eccentricity, axes, focus, perihelion, and aphelion distances against independent reference calculations.
- Checks that the history arrays all have `num_steps + 1` rows and remain aligned with `time_history`.

For every numerical test, record the inputs, expected results, units, tolerance, actual result, and pass/fail outcome. For input-validation tests, record the expected error message or rejection behaviour.

**Implementation-scope note:** the single script shown here does not define a separate automated test runner or automated assertions. It performs runtime checks and calculates validation diagnostics, but the cases above must be executed manually or implemented in a separate test script. Likewise, the code compares two methods for one selected `dt` per run; a multiple-time-step convergence study requires repeating the run with several `dt` values or adding a dedicated test harness.

## Assumptions and Limitations

The current prototype has the following assumptions and limitations:

- The system contains one fixed central star and one orbiting planet.
- Motion is two-dimensional.
- The star is stationary at the origin; star motion and barycentric coordinates are not modelled.
- The gravitational field is Newtonian and the star is treated as a point mass.
- The planet mass is validated and printed, but it does not affect the calculated acceleration.
- No other gravitational bodies or non-gravitational forces are included.
- Only bound elliptical initial conditions with negative specific orbital energy and non-zero specific angular momentum are accepted.
- The model rejects zero initial distance and checks for invalid positions and non-finite results during integration.
- The analytical ellipse is generated geometrically. The script does not calculate a time-matched analytical position at every numerical timestamp.
- The ellipse-distance diagnostic uses the closest of 3,601 sampled points, so it is an approximation to distance from the continuous ellipse and is not the same as a time-matched position error.
- The script does not automatically run a time-step convergence sweep; convergence must be evaluated by repeating runs or adding a test harness.
- Both integration methods are executed each run. The current script does not prompt the user to select only one method.
- The program does not calculate the orbital period in the provided code, even though an orbital-period estimate appears in the broader development roadmap.
- The numerical methods are not exact. Large time steps, highly eccentric orbits, or long integrations may produce significant errors or invalid numerical states.
- The point-mass model is not intended to represent every real astronomical effect.

### Implementation details to check before a release

Two labels in the current script should be corrected for the README and output to remain scientifically precise:

1. In the “Final State (Velocity Verlet)” section, the lines labelled `X-acceleration`, `Y-acceleration`, and `Acceleration magnitude` read `planet_accelerations(1, :)`, which is the **initial** acceleration. To print the final acceleration, use `planet_accelerations(end, :)` and calculate its magnitude from those final components. Alternatively, explicitly relabel the output as initial acceleration.
2. The graph currently titled `Euler vs Velocity Verlet: Trajectory Error` plots distance to the sampled analytical ellipse, not a time-matched trajectory error. Rename the title and y-axis to “Distance to Sampled Analytical Ellipse” and “Geometric Distance (m)”, respectively.

These corrections do not change the underlying integration method, but they prevent the output labels from implying a different quantity than the code calculates.

## Current State and Future Development

The current prototype demonstrates the geometry of a bound Keplerian ellipse and compares two numerical integration methods under a fixed-star inverse-square gravitational model. It is suitable as a foundation for the orbital mechanics branch of AstPIE because the analytical quantities, numerical state histories, and plots can be used to explain the relationship between initial conditions, orbit shape, and numerical accuracy.

Potential next steps include:

- Adding a separate automated test script with independent reference cases and defined tolerances.
- Automating time-step convergence tests for both numerical methods.
- Adding a time-matched analytical position history, using a suitable solution of Kepler's equation, to measure position errors at matching timestamps.
- Correcting the acceleration-output and ellipse-distance plot labels identified above.
- Adding an orbital-period calculation with clearly stated assumptions and validating it independently.
- Separating the physics calculations, integration routines, plotting, and tests into reusable functions or files as the prototype grows.
- Extending the model only after defining the new physical assumptions and corresponding validation strategy.

The current code should remain the reference baseline for these changes. New capabilities should preserve reproducible inputs and outputs, document the relevant physical equations, and be accompanied by tests that distinguish physical behaviour from numerical error.
